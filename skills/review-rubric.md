# Review Rubric — 审稿规范

> Review Agent 评审时按需读取。源自 academic-paper-reviewer + AI-Research-SKILLs 精华提炼。

## 先认清章节类型,再套判据(最重要)

提示词里有一句 `This is a <type> chapter`,它决定你用哪套标准。**套错标准的代价很大**:
你的 MUST FIX 清单会被冻结成验收单,Draft 要花最多 4 轮去满足它——如果里面塞的是
这章本来就不该报的东西,那 4 轮全是白烧。

| chapter family | 判什么 | **明确不许要求什么** |
|---|---|---|
| `idea`(method/related/background/theory) | 机制是否**解释**了而非只**断言**;设计选择有无理由;是否跑偏成结果复述 | **不许索要更多实验数字、统计显著性、baseline 对比**。缺指标不是缺陷,那是结果章的事 |
| `data`(results/experiments/analysis/ablation) | 每个数字是不是 `{{RES-xxx}}` 占位符/程序渲染的表(手打数字能否对回结果表);对比是否讲清楚;结论是否强于数据 | **不许索要实验标准差、方差、误差棒或方法设计阐述、也不许要求补写"缺什么实验/没有方差"之类的说明**——没有的就不写 |
| `mixed`(discussion/limitations/conclusion) | 解释是否有已建立的发现支撑;是否提炼意义与边界;有无引入作者没声称过的贡献 | 不要求每条解释重复具体数字，不把讨论改成第二遍结果报告 |

数字门禁级别也在提示词里:
- `advisory` → 结果库为空**本身不是缺陷**(方法章可以先于实验写)
- `off` → 这章是纯论述,不报任何指标是**正确的**

### 章节契约
提示词里的 `CHAPTER CONTRACT CHECK (<type>)` 是本章的写作契约:违反 Forbidden 或 References
规则 → MUST FIX。`contract-check.md`(若有)是程序粗检,逐条判断是否真违约,误报不必列为
MUST FIX。**不许以"创新性不足""与已有工作重合"为由提 MUST FIX**——创新性由作者负责。

## 用检查单,不用打分
系统提示词里的 10 项是/否检查单是判定依据:每项一个答案 + 一句证据。研究表明二元检查项比 1–5 打分
稳定得多,而且“否”可以直接变成 MUST FIX / SHOULD FIX。各章类型的具体判据见上表和下面几节,
它们决定哪些检查项适用(不适用就答 n.a.,不要为了凑数硬报问题)。

## 每条批评必须三要素
**what's wrong + where(具体位置)+ how to fix(具体改法)**。
禁止:fabricating review comments、generic feedback("could be improved")、sycophantic score inflation(无根据给高分)、**向本类型不该负责的内容索要证据**。

## 整章论证与内容取舍（每次初审必查）
先概括本章的中心问题与读者应获得的结论，再按段落作用检查论证是否成立。在 `Editorial assessment` 中给出判断，有问题才给具体删并建议，并同步到 Issues 及 JSON。
- 正文是否被运行清单、文件来源、核验步骤、逐格报数占据，导致必需的科学解释缺失？引用具体段落、指出未回答的问题和有限的改法。这种实质跑题可列 MUST FIX，进入既有冻结验收清单。
- 检查论证展开是否充分。指出引言过渡、公式直觉、设计理由、结果反例或讨论边界中具体缺失的一步，并定位可用的支撑材料。一般记 SHOULD FIX，直接影响核心结论且有可核查证据时才升 MUST FIX。不得要求补造原因、实验、标准差或调参流水账。
- 局部重复、稍长的段落、可接受措辞之间的偏好仍是 SHOULD FIX / CONSIDER，不因“像报告”的主观印象升级，不要求固定删减比例。
- 检查贡献是否有主次，核心设计是否被常规配置淹没，讨论是否在解释而非再报结果。建议应优先删并重复内容，不能习惯性地要求补更多说明。
- 不删指标分母、数据划分、关键假设、公平比较条件、重要反例与不确定性；不以压缩篇幅为由让结论变强。
- 内部追溯靠证据包、占位符和对账记录；正文无需逐段展示来源及核验过程。不要要求不存在的补充实验或附录。

## 顶会写法对照(只报能指出具体句子的差距)
按 `top-venue-craft.md` 的标准,下面这些是**值得报**的真问题(SHOULD FIX,影响理解时才升 MUST FIX):
- 引言的贡献不具体、不可证伪("提出了新框架,效果很好"),或没有指向支撑它的章节;
- 方法章只给公式不给直觉,或只讲"是什么"不讲"为什么这样设计";
- 实验小节不先说它要验证的论断,直接堆数字;解读只是重述表格;
- 相关工作逐篇罗列、没有说明与本文的关系;
- 反复罗列“没做什么”或自我辩护的段落应删并；必要的科学条件保留，综合局限按审定大纲集中表达；
- 段首或节末出现指向其他章节的导航句("如摘要所述""下一章将……""结论部分会……"),应删;
- 英美拼写混用(analyse/analyze、modelling/modeling),统一为美式。
- 贡献条目把同一件事讲两三遍(每条贡献 2 句足够:做了什么、证据在哪一节),应压缩;
- 正文把工作流用语写进论文(supplied / provided / attached 的材料、索引、笔记、大纲),应改成直接陈述事实;
- 用裸章名当地点("in Results""Method provides"),应改成 `[[SEC:标题]]` 占位符。

## 创新点忠实度检查(idea 类章节关键)
逐条对照 `idea.md`(作者的全局文档,读全文):
- 正文声称的贡献,是否都在 idea.md 的贡献清单里? → 超出的**必须** MUST FIX
- 核心洞察被弱化或改写了吗? → 改写作者的论断是 MUST FIX
- 机制只说了"做什么",没说"为什么work"? → MUST FIX(这是 idea 章的核心失效模式)
- 关键设计选择没给理由? → MUST FIX,但如果 idea.md 本身没写,**标给作者**而不是让 Draft 编
- 出现 `[DESIGN DETAIL NEEDED]` 标记? → **这是正确行为**,不是缺陷。转成给作者的待办

## 数据-结论 mismatch 检查(data 类章节关键)
每查一个论断,核对它对应的数据:
- 数据 p=.12 却说"显著改善" → **必须** MUST FIX
- 声称"基线公平"但没对比结果 → 标记证据缺失
- 本文实验出现结果表(数据索引)里没有的手打数字 → **必须** MUST FIX(number-check.md 会先机械抓一遍)
- 声称类型↔证据设计匹配:
  - 因果声称 → 需消融实验
  - 改进声称 → 需基线对比
  - 泛化声称 → 需异质测试

## Devil's Advocate 挑战
每篇至少挑战一次"最能证明贡献的点",但挑战点要落在本章类型能负责的范围内:
- idea 章:核心洞察的因果链是否断裂?有没有更简单的解释能达到同样效果?
- data 章:基础是否崩塌(数据与结论不符)?是否存在更强的反叙事?

## 防谄媚与自我偏好
- 你没有写这份草稿:按外部审稿人的立场读,答案要有文本证据。**拿不准时不要升级成 MUST FIX**:
  无法指出具体错句的疑虑记为 CONSIDER;有具体错句但只是表达问题记为 SHOULD FIX。
  MUST FIX 只留给"文本本身错了/误导/跑题,且起草者改文字就能修"的问题
- 实质跑题可定位到具体段落及未完成的章节任务，不要求先找到一个事实错句；局部风格偏好仍不升级。
- 不参考任何以前的分数或结论,只判断眼前这份文本
- 验收标准保持稳定，以证据判断修复是否成立；不得因前轮修改次数提高门槛或追加冻结清单外的问题

## 输出顺序
按严重度排序:MUST FIX / SHOULD FIX / CONSIDER,每条带具体位置 + 证据定位 + 改法。不挑错式评审,每处建议必须建设性。

## 与 review-v1.json 的关系
本规范指导 Markdown 评审(review-v1.md)的内容质量;结构化 JSON(review-v1.json)承载 must_fix 清单 + needs_citation,供编排层消费。

### 精炼度硬红线（违反以下任意一条直接列 MUST FIX）
- **出现标准差描述**：实验结果正文、表题、表注或图注中出现 `±`、`\pm`、`std`、`standard deviation`、`standard error` 等描述 → **MUST FIX**（直接删除，只保留均值）。
- **实验设置成过程流水账或单开指标小节**：专门设章/小节或用多段科普常规指标（如 Accuracy、Macro-F1），或将完整实验流程、超参搜索网格、回退规则、各组统计家族明细搬进正文 → **MUST FIX**（压缩为高层次协议，数据集改汇总小表，常规指标一句话带过）。
- **表注越界**：`[TABLE: ...]` 的 `note:` 超过 2 行（约 30 词），或在表注里定义消融变体、说明实验口径、解读结果数据 → **MUST FIX**（移回正文对应段落，表注仅保留极简符号约定）。
- **正文表格指标过多或含重复列**：正文 `[TABLE: ...]` 渲染超过 6 个指标列，或未用 `cols:` 过滤掉次要/重复列 → **MUST FIX**（使用 `cols:` 只保留重要指标列）。
- **引言拆节/贡献冗余，或相关工作逐篇写小作文**：未经作者指定的引言出现 `1.1/1.2` 子标题、贡献前有重复铺垫或每条超过 2 句；相关工作单篇展开超过 2 句且每节末尾重复推销本文方法 → **MUST FIX**（合并删减）。

### 方法论硬红线（按下列严重度记录）
- **出现数学证明或分步推导**：正文包含 `Proof`、`Lemma`、定理证明或分步代数/求导推导过程 → **MUST FIX**（直接删除推导过程，仅保留最终公式与一句直白结论）。
- **摘要超过 7 句或结构错位**：摘要总句数 $> 7$ 句，或未按“第 1 句背景 → 第 2 句问题 → 中间用 3–4 句讲方法与贡献 → 末句结果”组织 → **MUST FIX**（严格压缩至 $\le 7$ 句并对齐句位职能）。
- **引言结构偏离或前人评述失控**：
  1. 引言出现 `1.1/1.2` 二级标题；
  2. 未按“1–2 段扩写摘要 → 3–4 段评述前人优缺点 → 简述本文方法与贡献”展开；
  3. 第 3–4 段对单个前人方法展开多句冗长介绍（引言中每项前人方法必须精炼为**一句话**讲清提出了什么、优点和缺点，详细展开应留给 Related Work），或前人缺点与本文要解决的问题脱节；
  4. 读完引言仍需要猜测本文核心方法/Idea。
  以上任一项 → **MUST FIX**。
- **表达晦涩、用词啰嗦**：能用一个词表达却堆砌繁复词组、长难句绕弯，导致读者难以一眼看懂方法 → **SHOULD FIX**（影响核心 Idea 理解时升 **MUST FIX**）。

作者在大纲中明确安排的 appendix 附录可容纳材料中已有的证明和推导；上述正文禁推导规则不用于该附录，不得编造或自行补写证明。

实验比较中明确归属于他文、紧跟有效引用且有笔记支撑的原文数字可直接转述，不按本文手打结果报错；仅带引用的本文结果仍按数据索引核验，相关工作章仍不写他文数字。
